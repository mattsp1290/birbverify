# Proposed failure experiments

Status is PROPOSED EXECUTABLE TESTS, NOT EXECUTED PROOF.
No row below passed runtime acceptance in this assignment. The existing source tests establish only the boundaries described in [the design](design.md).

## Invariants

- I1. After a committed request seal, that request can never acquire another token or commit a target mutation through worker authority.
- I2. Release requires attributable stop and cleanup, or target proof that execution never acquired. Fencing alone is insufficient for an acquired attempt.
- I3. Closure identity, request digest, target incarnation, epoch, and resolved attempt cannot change on replay.
- I4. Every ambiguous effect is reconciled by stable operation identity before another effect. A later owner can never be released by replay of an old closure.
- I5. Historical manifests and attempt budgets are immutable. Closure never supplies an application verdict or delivery eligibility.
- I6. Birbforge advances only after the blocked head's valid closure and a current matching free-target observation. Request termination and availability are separate facts.
- I7. The target journal survives restart without losing a seal, identity binding, or committed receipt. Known incomplete history or an operator-declared restore denies release until reconciliation. Silent in-place rollback is outside the fixture trust assumption and is not claimed detectable.

## Fixture method

The implementation milestone creates a new private Linux fixture root with synthetic requests, an isolated SQLite target, the real producer activity, and disposable Docker containers. It does not reuse the stopped consumer runtime or contact staging. Barriers pause execution at named boundaries, not elapsed sleeps. A daemon proxy or controlled lifecycle adapter can withhold delivery and replies for the exact fixture operations. Fault controls never ship as ordinary client authority.

Target-only races use independent target connections and `BEGIN IMMEDIATE`, not only the current serial Unix server handler. End-to-end cases additionally use a real Temporal activity. Fixtures capture operation counts, target snapshots with revisions, process identity evidence, Docker control intent/settlement records, and immutable digest comparisons. The implementation records exact source and adapter revisions with each result.

Proposed producer tests belong in `tests/test_target.py`, `tests/test_journeys.py`, and a dedicated closure test module. A fixture-only queue driver can model waiting without editing the consumer. Later consumer integration runs the mapped `verification_python` tests separately.

A separate destructive *counterexample experiment* may restore an old fixture database without declaring the restore while a worker is paused. It demonstrates that a database-local revision cannot detect its own rollback, especially after a lost reservation reply. This experiment is expected to invalidate the guarantee and is NOT an acceptance pass. It requires an isolated disposable fixture and must never run against either pinned checkout's old runtime. The supported F20 test uses the operator-declared restore path, a new incarnation, and prior-execution reconciliation.

## Acceptance boundary

The producer owner must execute every applicable row and retain failures, including intended quarantines. A correct quarantine assertion is a safety pass for that scenario, not evidence that automatic recovery succeeded. F10 must prove that the uncertain daemon case remains blocked unless a separately supported settlement mechanism is exercised.

F01-F07 and F12-F17 need both direct transaction tests and selected real activity interruption tests. F11 needs a queue observation driver now and the actual Birbforge queue in the later integration milestone. F18 must preserve the previously exercised known-context behavior. Source review alone cannot close any executable gate.

Staging mutation, native isolation, production actor authentication, artifact retention, and physical client journeys remain separate acceptance gates. A successful fixture matrix must not be reported as any of those proofs.
